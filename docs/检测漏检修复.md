# MediaPipe 小手/边缘手漏检修复（2026-11-03）

## 复现与判断

核对了 HOT3D 原生1201-1/1201-2、顺时针90°正向、裁剪后的坐标还原及FISHEYE624映射。已有全图推理在灰度、小手、视野边缘和遮挡条件下会漏检；这不是“画面中有手就一定检出”的模型保证。

40个固定视图的先导实验中，原全图有手输出8个视图；相同0.5分数阈值的固定重叠裁剪在其中10个全图漏检视图找回了手。没有使用GT框。完整验证随后使用三个训练片段全部450帧，未按成败重新挑选帧。

## 修改范围

- `detection/mediapipe_detector.py`：先原全图推理；仅完全零检出时对四个65%宽高、互相重叠的固定区域重试。已成功全图原样返回。
- 重试仍用同一官方模型、同样分数阈值。裁剪坐标平移回完整输入图；归一化x/y及模型z尺度相应还原，再执行HOT3D正向像素恢复/官方射线映射。
- 相邻裁剪的同一只手按对应关键点距离去重，不用左右手标签当身份；至少16个关节须在该裁剪内，裁剪外点标无效。输出不超过num_hands。
- VIDEO每帧仍只向视频实例提交一次时间戳；裁剪重试使用延迟创建的独立IMAGE实例，避免重复时间戳与错误视频跟踪状态。关闭时释放两个实例。
- 原始检测与补救来源、尝试次数、有效配置写入诊断。录制模型元数据与benchmark检测快照保存补救设置。三维匹配、骨长/极线/重投影门控保持原策略。
- 没有改变GUI布局、把GT补进预测或降低分数阈值。只提高部分漏检情况下的检出机会，不能保证严重遮挡/侧视下必检。

## 配置与生效

`configs/detector.yaml`末尾新增 `rescue`，由检测器直接读取，GUI与benchmark均生效：

```yaml
rescue:
  enabled: true
  crop_fraction: 0.65
  duplicate_distance_fraction: 0.25
  min_inside_joints: 16
  min_image_side_px: 128
```

可设置enabled=false恢复单次全图行为；API也支持构造参数rescue_config覆盖。源码修改后需退出并重新启动当前运行的Python/GUI进程；仅在旧进程中暂停/继续不会重新加载代码。此后修改配置需重建检测器。

## 实际结果

相同片段001849/001851/001894、相同顺序、450帧，真实MediaPipe原生灰度正向推理：

|指标|原全图基线|开启零检出补救|
|---|---:|---:|
|左图有检测帧|21 (4.67%)|116 (25.78%)|
|右图有检测帧|29 (6.44%)|182 (40.44%)|
|同帧双路有检测|0|30 (6.67%)|
|任一路有检测|50 (11.11%)|268 (59.56%)|
|被接受立体对|0|7|
|有效三维关节输出|0|107|
|可比较有效GT关节|0|103 / 18000 (0.57%)|
|有效点MPJPE|N/A|17.35mm，P95 45.71mm，最大91.04mm|

检测率只是图中存在模型输出的比例，不等于每只手均正确识别。三维覆盖率仍然很低，不能只用有效点17.35mm宣称整体精度优秀或问题全部解决。余下困难帧仍可能漏检或被几何拒绝。

片段001851第0帧（与用户截图相同键盘操作场景）：左右检出数由0/1变为1/1；该帧仍未通过可靠三维对应门控，三维保持无效。修复前后图和完整诊断在 `logs/detection_diagnosis/visible_hand_before_after.json`、同目录 `clip001851_frame0_before.png / after.png`。

代价是空检测帧最多额外4次模型推理。完整450帧含读取/重采样/诊断/失败保存，约7.28FPS；原生全图历史运行约26.86FPS，两次运行的机器负载不同，不能当严谨微基准。正常全图有结果时不增加裁剪推理。
