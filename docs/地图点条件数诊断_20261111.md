# 地图点信息矩阵条件数诊断（2026-11-11）

给 `FullInertialBA` 补的第一个"数值层面"原生指标：每个地图点顶点的 3×3 信息矩阵条件数。
目的是回答总报告（`docs/VIO_跳变根因取证总报告_20261111.md` 第 5 节问题 1、第 6 节建议 2）留下的
"为什么部分地图点在一次求解里被推到公里级"。

结论先说：**条件数确实极高，但它并不是一个独立原因 —— 它基本上就是"这个点离相机多远"的另一种写法。**
本运行里 >100 m 的点在求解前半径中位已是 109 m（<1 m 组只有 2.59 m），
条件数对这些点的判别力（AUC 0.988）与"半径"本身的判别力（AUC 0.994）几乎相同；
在同一深度带内部，条件数与位移幅度基本不相关（Spearman 0.03）。详见第 5 节。

## 1. 改动点（只增不改）

### 1.1 新增诊断函数

`third_party/ORB_SLAM3/include/VioOptimizationDiagnostics.h`，在 `GraphMetrics()` 之后、
`NormalizeGauge()` 之前新增：

```cpp
inline void PointInformationMetrics(Map* map, unsigned long long event, const char* stage,
                                    g2o::SparseOptimizer& optimizer, unsigned long maxKFid)
```

行为：
- 只在 `VioDiagnostics::Enabled()`（环境变量 `EGOHAND_VIO_DIAGNOSTICS` 非空）时执行；
  否则立即返回，零开销、零文件。
- 用 `maxKFid` 复算 `FullInertialBA` 的点顶点 id：`point->mnId + maxKFid*5 + 1`（`iniMPid = maxKFid*5`）。
- 遍历 `optimizer.edges()`，对每条与点顶点相连的边按实际类型 `dynamic_cast` 分支：
  `EdgeMono` 取 2×3、`EdgeStereo` 取 3×3 的 `_jacobianOplusXi` 分块，累加 `J^T Ω J`（`Ω = edge->information()`）。
- 对称化 `H ← (H+Hᵀ)/2`，`SelfAdjointEigenSolver` 求特征值，
  `sigma_min/sigma_max = sqrt(max(eig,0))`，`condition_number = sigma_max / max(sigma_min, 1e-12)`。
- 只写一个文件 `<prefix>_point_condition.csv`；不加任何 stdout/stderr 输出；不改任何顶点、边或求解器状态。

输出列：

| 列 | 含义 |
| --- | --- |
| `id` | `MapPoint::mnId`，与 `<stage>_points.csv` 的 `id` 同义（便于直接 join）；对应 g2o 顶点 id 为 `id + maxKFid*5 + 1` |
| `observations` | `MapPoint::Observations()` |
| `edges` | **实际被累加**的边数（类型已知 + `linearizeOplus()` 结果有限） |
| `sigma_min` / `sigma_max` | 信息矩阵最小/最大特征值的平方根 |
| `condition_number` | `sigma_max / max(sigma_min, 1e-12)` |
| `trace` | 对称化后 `H` 的迹 |
| `valid` | `edges>0` 且 `H` 与谱全部有限 |

### 1.2 调用点

`third_party/ORB_SLAM3/src/Optimizer.cc` 的 `FullInertialBA`，在 `fullba_before` 与 `fullba_solved`
两处 `GraphMetrics(...)` 之后各加一行（其余逻辑一行未改）：

```cpp
VioDiagnostics::GraphMetrics(pMap,diagnosticEvent,"fullba_before",optimizer);
VioDiagnostics::PointInformationMetrics(pMap,diagnosticEvent,"fullba_before",optimizer,maxKFid);
const int completedIterations = optimizer.optimize(its);
VioDiagnostics::GraphSnapshot(pMap,diagnosticEvent,"fullba_solved",optimizer,...);
VioDiagnostics::GraphMetrics(pMap,diagnosticEvent,"fullba_solved",optimizer,completedIterations);
VioDiagnostics::PointInformationMetrics(pMap,diagnosticEvent,"fullba_solved",optimizer,maxKFid);
```

### 1.3 一个必须说明的实现细节（否则会崩）

g2o 这份 vendored 版本里 `_jacobianOplusXi/_jacobianOplusXj` 不是普通矩阵，而是
`Eigen::Map`（`Matrix<double,D,Di>::AlignedMapType`），构造时映射到 **空指针**（`_jacobianOplusXi(0, D, Di)`），
只有在 `BaseBinaryEdge::linearizeOplus(JacobianWorkspace&)` 里被 placement-new 重新绑定到工作区内存之后才可写。
`initializeOptimization()` 之后、`optimize()` 之前（正好是 `fullba_before` 的位置）还**没有**任何一次线性化，
此时直接调 0 参数 `linearizeOplus()` 会写空指针 —— 实测就是在 event2 的 `fullba_before` 处
`0xC0000005` 访问违例。因此实现里调用的是带工作区的重载：

```cpp
edge->linearizeOplus(optimizer.jacobianWorkspace());   // 先重绑定，再算 Jacobian
```

用的是求解器自己的 `_jacobianWorkspace`（`initializeOptimization()` 已 `allocate()`，
每槽位大小 = max(顶点维 × 误差维) ≥ 9 个 double），所以退出本函数后 Map 仍指向求解器自有内存，
不会留下悬垂指针，也不影响求解（`block_solver.hpp:531` 每次线性化都会重新绑定同一个工作区）。

## 4. 位移分组（本运行的实测）

分组口径：`non_rigid` = 同一 `id` 的点在 `fullba_before → fullba_solved` 的位置差，**先扣掉关键帧拟合出的刚体运动**
（`pose_alignment`，用同 id 关键帧）。必须这样做，因为本运行 event6 的整图刚体平移是 **142.606 m**
（54 个关键帧，旋转 1.938°，拟合残差 p95 0.179 m）—— 按原始位移分组会把 **1244/1244** 个点全塞进 >100 m，
分组就失去意义（这也是"整图重锚"在点云上的直接体现）。

| 事件 | 同 id 点 | 关键帧刚体平移 | <1 m | 1–100 m | >100 m |
| --- | ---: | ---: | ---: | ---: | ---: |
| event2 | 755 | 0.534 m | 721 | 33 | 1 |
| event4 | 889 | 0.186 m | 787 | 102 | **0** |
| event6 | 1244 | 142.606 m | 1040 | 97 | **107** |

各组的"求解前半径"与"被推多远"（event6）：

| 组 | 半径 p50 / p95 / max (m) | 位移 p50 / p95 / max (m) |
| --- | --- | --- |
| <1 m | 2.59 / 5.94 / 16.05 | 0.169 / 0.534 / 0.996 |
| 1–100 m | 5.31 / 63.29 / 164.26 | 2.048 / 50.12 / 92.68 |

→ 被推到公里级的点，**求解前就已经在百米量级**（中位 109 m，而稳定点中位 2.59 m）。
本次改动不改变这个事实，只是把它量化了。

### 5.3 结论

**问："被推到公里级的点，其信息矩阵条件数是否显著更高（接近奇异）？"**

**是，数值上非常显著**：event6 的 >100 m 组求解前条件数中位 **3 318**（稳定组 62.6，差 **53 倍**），
求解后 **30 770**（差 **487 倍**）；`sigma_min` 从 2.97 掉到 9.6e-4（求解前）/ 1.05e-5（求解后）。
AUC 0.988（求解前）、0.999（求解后）—— 几乎完美分开。

**但这不是一个新的、独立的原因，我不把它当"根因"上报，理由有三**：

1. **它和"离得多远"几乎等价**。条件数的判别力（0.988）并不高于点半径的判别力（0.994）；
   `sigma_max` 与半径的 Spearman 是 **-0.76**（点越远、Jacobian 越小、`sigma_max` 越小），
   `sigma_min` 掉得更快，比率才涨上去。也就是说，这个指标测到的主要是"深度方向的弱可观测性随距离恶化"，
   属于几何事实，不是求解器病态。
2. **在同类点内部它不排序**。把半径限制在 ≥50 m 的 101 个点（94 个被推走）里，
   条件数 AUC 仍有 0.903（能分开"会不会被推"），但与位移幅度的 Spearman 只有 **0.028**（100–300 m 带里是 -0.15）
   —— 条件数不能预测"被推 1 km 还是 3 km"，而本问题的痛点恰恰是幅度。
3. **与已知否定性证据一致**。`edges`（AUC 0.692）、`observations`（0.720）判别力弱，
   复现了此前"与边数/观测数不相关"的结论；真正强相关的是几何距离。

**因此：条件数不是"为什么被推到公里级"的独立解释，而是同一现象的另一种表述** ——
这些点在求解前就处在百米量级、深度方向的信息矩阵特征值已接近 0（`sigma_min` ~1e-3），
一次把惯性 chi2 压下去的自由度足以把它们沿这个近乎零空间的方向推出几百米到几公里。
要判断"是不是求解器数值 bug"，本指标给不出支持；它反而指向"远点 + 无深度约束"这一几何成因。
（与总报告第 4.4 节"畸变不集中在低观测点"、第 2.3 节"沿零空间滑走"的结论一致。）

## 6. 已知局限

1. **没有 robust kernel 权重**。累加用的是 `edge->information()`（用户设定的 `I·invSigma2`），
   不含 Huber 的 `rho'` 权重；求解器实际线性化时的有效权重是被 Huber 缩放过的。
   所以这里的 `H` 是"名义信息矩阵"，对 chi2 很大的边（离群/被拉坏的点）会**高估**其约束强度。
2. **只统计 `linearizeOplus()` 成功的边**。非有限的 Jacobian（深度 ≤0、`Xc(2)≈0`）会被跳过，
   `edges` 列就是成功累加数。本次运行未发生跳过（见 3.1），但这意味着
   **本指标在"某个点已被推坏到无法线性化"时不描述该点**——即它看到的多是"坏之前"的状态。
3. **`sigma_min/sigma_max` 强烈依赖 Jacobian 尺度**（∝ 焦距/深度），跨深度的绝对值不可直接比较；
   条件数本身是比值、对整体尺度不敏感，但对**各向异性**敏感，而各向异性又随深度单调变化
   （本报告 5.2 节即为此问题的量化）。因此"条件数 3e3 算不算大"没有通用阈值，只能同批比较。
4. **求解后的条件数含因果混淆**：点被推远 → Jacobian 变小 → 条件数变大。
   求解后的数值（30 770）不能当作"求解前就如此"的证据；本报告的因果判断以求解前的数值为准（3 318）。
5. **`id` 是 `MapPoint::mnId`，不是 g2o 顶点 id**（顶点 id = `mnId + maxKFid*5 + 1`）。
   要与 `_edges.csv`（顶点 id）对齐时需要做一次换算；本报告 3.1 节的自检已按此换算核对。
6. **单次运行、单条录制**。本运行 event4 一个 >100 m 的点都没有（总报告里那次是 27/816），
   event6 是 107/1244（此前 75/816）；ORB 调度带来的运行间差异很大，分组的**绝对条数**不可跨运行比较，
   "同一次求解内、同 id、同阶段"的组间对比才是可比的。
7. **`ignored` 计数没有落盘**（按约束不许写第二个文件），只能靠 `_edges.csv` 的边类型清单间接核对；
   本次核对结论是 0（见 3.1）。
8. 诊断开启本身会改变调度与耗时（本次 track_ms p50 56.5 vs 对照 35.9/62.4），
   故本报告的所有数字只能与同臂诊断运行的内部对比，不能当性能或线上指标。
