# 地图点止血：实现与首次对照（否定结果，2026-11-11）

配套：`docs/地图点止血_设计方案_20261111.md`（设计）、`docs/地图点深度发散_根因链_20261111.md`（根因链）

---

## 1. 实现了什么

在 `FullInertialBA`（`Optimizer.cc`）加了 **opt-in 的地图点止血**：

1. **求解前**捕获所有参与优化的地图点位置（`pointBefore`），与关键帧位姿捕获同步；
2. 复用 `VioWorldFrame::FitRigid` 得到的**整体 SE(3)**（同一套同 ID 关键帧拟合，`worldFitForClamp`）；
3. **回写时**（`nLoopId==0` 分支）把求解前位置经刚体变换预测到求解后世界，比较残差：
   `residual = || p_solved − (s·R·p_before + t) ||`
   若 `residual > max(1.0 m, 5% × |p_predicted|)` → **不写回**（保留旧位置）并计数。

开关：`EGOHAND_VIO_POINT_CLAMP=1`（默认关闭）；阈值可用 `EGOHAND_VIO_POINT_CLAMP_FLOOR_M` / `EGOHAND_VIO_POINT_CLAMP_FRACTION` 覆盖。

DLL：`src/egohand/vio/native/bin/egohand_vio_point_clamp.dll`（19:46，含 `world_frame_revision` 能力）。

**ON 臂在所有事件上都更差**，与"止血应减少畸变"的预期相反。

## 3. 为什么这次对照不能下结论（四条硬伤）

1. **两次运行的地图演化本就不同**：event6 点数 OFF 1382 vs ON **852**（差 38%）。说明两次运行走了不同的建图路径，不是配对对照。ORB 的建图对调度敏感，`docs/VIO_ACCEPTANCE_REPORT.md` 已记录过同类现象（同配置重复跑指标差异大）。
2. **缺少拦截计数输出（实现缺口）**：`PointClampCounter()` 已经实现，但**没有接到桥接层/Python/poses.jsonl**，所以本次无法确认"到底拦了多少点"。没有这个数，就无法判断"ON 更差"是因为止血逻辑有害，还是因为两次运行的随机差异。
3. **单次运行、未重复**：所有此前的经验都表明单次对照会被 run-to-run 方差淹没（实验 C 就是 n=2 时"有效"、n=5 时"无效"）。
4. **⚠️ 实现本身有设计缺陷（最关键）**：`FullInertialBA` 里**关键帧位姿在 812–867 行就已写回**（`pKFi->SetPose(Tcw)`），点回写在其后（869 行）。所以"不写回 = 保留旧位置"会让**地图点与关键帧位姿不自洽** → 重投影误差反而变大 → 下一次 Local BA 更糟。**这很可能就是 ON 臂更差的原因，而不是阈值问题。**

→ **诚实结论：这次对照既不支持也不否定止血方案，它是无效实验，且实现有已知缺陷。**

## 4. 修正后的方案（两个层次）

### 4.1 已改：把"保留旧位置"改为"标记 bad"，并把计数暴露出来

**改动 1 — 动作改为 `SetBadFlag()`**：关键帧位姿在点回写之前就已更新，保留旧坐标会造成地图与位姿不自洽。改为从地图移除，避免留下不一致的几何。

**改动 2 — ABI 安全的计数导出**：
- 最初把 `point_clamp_rejected` 加进 `EgohandVioWorldFrameInfo` 结构体，**这是错的**：Python 侧对 `struct_size` 做严格相等校验，中途插字段会让 v9 / safe_exp / point_cond 等既有 DLL 全部报 ABI 不匹配。
- 已撤回，改为**独立导出函数** `uint64_t egohand_vio_point_clamp_count(void)`。旧 DLL 没有该符号时，Python 侧可用 `getattr` 优雅降级，结构体尺寸保持原样（已核：`EgohandVioWorldFrameInfo` 无 `point_clamp` 字段，11 项 ABI 相关测试通过）。
- 重建：`egohand_vio_point_clamp.dll`（20:19，sha256 `cb1ba549…`）；`live_timing.yaml` 与 `v9` 时间戳未变。

### 4.2 根本方向可能不在这里（重要反思）

止血只是"事后丢弃"，而远点是**持续产生**的：
- 三角化门限 `cosParallaxStereo = cos(2·atan2(mb/2, depth))` 随深度趋近 1 → 越远越宽松（已实测）；
- `mfMaxDistance` 相对自身距离定义 → 远点上界随之膨胀；
- `System.thFarPoints` 只在**创建时**过滤（已实测不足以修复）。

因此即使把被推远的点标 bad，**下一轮仍会有新的远点被推**——只是把"推远"换成"丢弃"，地图会持续失血。

真正需要在**三角化阶段**决定"这个点值不值得进图"：
- 加**绝对深度上限**（不是相对 `mfMaxDistance`）：`depth > k·baseline` 直接拒绝；
- 或对三角化结果检查**视差是否足以约束深度**（`cosParallaxRays` 与等效基线视差的比较已在做，但远点处判据失效）。

→ **结论：止血可以作为临时保护，但不应作为主修复方向。** 主方向应是"远点准入"。

## 5. 下一步（按优先级，含"先验证再投入"）

1. **补拦截计数可观测性**（必须先做）：`PointClampCounter()` 经 ABI 暴露 → 写入 `poses.jsonl` 的 `point_clamp` 字段。否则任何对照都无法归因。
2. **改为标记 bad**，再对照（含 4.1 的安全性核对）。
3. **同时验证 4.2 的假设**：统计"每轮新建点中远点占比"，若远点持续产生，则止血必然无法根治 —— 这一步能决定是否值得继续投入止血。
4. 每组 ≥5 次、固定调度、报分位数区间。
