# 客户端 GUI 词典常驻修复（2026-11-12）

## 1. 问题

客户端交付版 GUI（`userrr/client_gui.py`）每次点「开始」都要等约 **28 秒**才进入定位，原因是 ORB 词典 `ORBvoc.txt`（约 145 MB）被反复重新加载。

## 2. 根因（两条独立路径，都缺复用）

| 路径 | 原实现 | 后果 |
| --- | --- | --- |
| **设备实时** | 客户端从不创建 `LiveVioWorker`，`SessionController.start` 也不传 `vio_worker`；`LiveVio` 因此 `_owns_worker=True`，在会话结束时 `worker.close()` | 每会话一个子进程，进程内加载词典 → 结束后销毁 → 下次重新加载 |
| **录制回放** | `ReplayBridge.start()` 直接 `Popen([PYTHON,'-m','egohand.vio.live_subprocess', port])`（一次性模式）；该进程 `open_bridge()` 后只服务一次就退出 | 每次回放都重新读词典 |

参照：原 GUI `src/egohand/gui/main_window.py` 本来是对的——窗口级 `LiveVioWorker()`（第 82 行）、传入 `vio_worker=`（第 301 行）、退出时 `close()`（第 750 行）。客户端 GUI 没有搬这套。

而子进程侧**早就有**常驻模式：`live_subprocess.py` 的 `--live-sessions` 在一个 `ExitStack` 里只建一个 `bridge`（词典只读一次），会话之间用 `bridge.reset()` 复位地图。缺的只是没人用它。

## 3. 改动

### 3.1 `src/egohand/vio/replay_runtime.py`

- `ReplayBridge.__init__` 新增 `worker=None`；有 worker 时**不** `Popen`，改为向常驻进程请求一个会话：
  ```python
  _proc, self.reused_worker, _log = self.worker.request_session(
      listener.getsockname()[1], self.settings_path, self.log_path.parent.name, mode=self.mode)
  ```
  同时不接管日志文件（`self.log=None`），`_reap()` 因 `self.proc is None`、`self.log is None` 自动跳过——**回放结束不会杀掉 GUI 的常驻进程**。
- `ReplayVio.__init__` 新增 `worker=None` 并透传给 `ReplayBridge`。
- 回放起点状态区分「复用已加载词典」与「已就绪」；用 `getattr(bridge,'reused_worker',False)` 兼容测试替身。

### 3.2 `src/egohand/gui/workers.py`

`ReplayVio(..., worker=self.vio_worker)`——把 `PipelineWorker` 收到的共享 worker 传给回放。

### 3.3 `userrr/client_gui.py`

- `from egohand.vio.live_runtime import LiveVioWorker`
- 窗口构造：`self.live_vio_worker=LiveVioWorker()`
- `session.start(..., vio_worker=self.live_vio_worker, ...)`
- `closeEvent`：`self.live_vio_worker.close()`（**只有真正退出 GUI 才释放**）

### 3.4 `tests/test_vio_vocabulary_reuse.py`（新增，4 项）

锁住三件事：共享模式下不得 `Popen`、回放结束不得关闭 GUI 的 worker、`ReplayVio` 必须透传 worker、客户端 GUI 必须持有并在 `closeEvent` 释放。

## 4. 实测效果

同一 settings、同一 DLL，直接测 `ReplayBridge.start()`（含握手=词典加载完成）：

| 场景 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | ---: | ---: | ---: |
| **旧行为**（每次一次性子进程） | 27.59 s | 28.89 s | — |
| **新行为**（共享 worker） | 27.59 s | **0.01 s** | **0.01 s** |

子进程 PID 全程不变（17268），说明是同一个 ORB 进程在复用。

worker 层同样验证：连续两次 `request_session` 返回同一 PID，耗时 0.02 s / 0.05 s。

## 6. 诚实的边界（必须知道）

1. **首次仍要 27.6 秒**。词典必须在新进程里读一次，无法避免。
2. **换 settings 会重新加载**。`LiveVioWorker` 的身份是
   `(mode, settings路径, settings哈希, 库路径, 库哈希)`，任一变化就重启子进程。
   实测回放用的是**录制自带**的 `vio_settings.yaml`，与 `live_timing.yaml` 解析出的 live settings **不同**：
   ```
   live      : configs/vio/vs030_rectified_half_calibration2.yaml
   recording : data/imu/session_.../vio_settings.yaml   → 不相同
   ```
   所以「同一录制反复回放」是 0.01 秒；**换了另一份标定快照不同的录制，仍要重载一次**。这是正确性优先的行为，不是 bug。
3. **刻意没有做"GUI 启动即预加载"**。回放的 settings 是按录制解析的，若用 live 配置预加载，回放一开始就会因身份不同而重启，反而多等一次 28 秒。宁可让首次会话承担，也不做会适得其反的预加载。
4. **同一时刻只服务一个会话**。常驻进程按 stdin 逐条处理，回放进行中不能并行开第二个 VIO 会话。
5. **未实机验收**。以上都是离线进程/回放层面的验证；设备实时链路的实际观感需在 GUI 里确认。

## 7. 复现

```powershell
# 回归
.\.venv\Scripts\python.exe -m pytest tests\test_vio_vocabulary_reuse.py tests\test_vio_replay.py -q

# 实测复用耗时
.\.venv\Scripts\python.exe -X utf8 -c @"
import time
from pathlib import Path
from egohand.vio.live_runtime import LiveVioWorker
from egohand.vio.replay_runtime import ReplayBridge
from egohand.vio.config_snapshot import resolve_live_config
cfg=resolve_live_config(); out=Path('logs/vocab_reuse_probe'); out.mkdir(parents=True,exist_ok=True)
def timed(worker,tag):
    t0=time.perf_counter(); b=ReplayBridge(out/f'{tag}.log',settings_path=cfg.settings,worker=worker)
    b.start(); dt=time.perf_counter()-t0; b.close(); return dt
w=LiveVioWorker()
for i in (1,2): print('replay %d: %.2fs' % (i, timed(w,f'shared{i}')))
w.close()
"@
```

## 8. 建议的后续

1. 实机确认：连续「开始/停止」多次，观察第二次起是否瞬时进入。
2. 若希望**首次也快**，需要让词典在进程间共享（例如把 `ORBvoc.txt` 预序列化为二进制，或让常驻进程在 GUI 启动后立刻预热 *live* 配置）。后者只在设备实时场景有效——回放仍会因 settings 不同而重载。
3. 客户端 GUI 可考虑在状态栏常显「词典：已加载 / 加载中」，把当前 27.6 秒的等待变成可解释进度。
