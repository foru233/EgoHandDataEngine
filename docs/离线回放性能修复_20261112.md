# 离线回放性能修复（2026-11-12）

用户反馈 VS030 原生录制回放只有 2–3 FPS。最近实际客户会话 `userrr/sessions/replay_1794448244420781000/replay.json` 记录 215 帧 / 83.205 秒（含启动），约 2.58 FPS。

## 原因和改动

- 实时源名为 `vendor_vs030`，原生录制源名为 `vs030_recorded`。原先后者没有进入实时检测配置分支：全图无手时每侧还调用四次裁剪补检，而且双目检测串行。初步 profiling 记录在 `results/performance/offline_before_20261112/profile.pstats`；profiling 有额外开销，不与后面的无 profiling 数据直接比较。
- 按用户要求，`configs/app.yaml` 新增 `vs030_rescue_enabled: false`，同时关闭 VS030 实时/原生录制裁剪补检。每帧仍运行左右全图检测，原数据集设置不变。需要恢复时可设为 true；区域数分别用既有 `vs030_rescue_crops_per_frame` 和新增 `vs030_recorded_rescue_crops_per_frame` 配置。
- 双目检测器各有独立实例，左右并行，帧间仍等待两侧完成，保留时序和离线完整处理。未改 VIO DLL、标定、IMU 时序、质量门限、输入分辨率或输入帧数。
- GUI 处理 FPS 改用最近 30 个完成间隔，包含逐帧解码/VIO/检测工作，不包含启动词典的等待；暂停或跳转重置窗口。实际停顿仍进入统计，没有靠过滤慢帧提高显示值。

## 实际录制对照

录制：`data/imu/session_20261111_105436_609132400`，前 120 帧。通过同一个真实 `PipelineWorker` 和现行 native 子进程测量，使用同一 Python 环境，无 profiling、串行运行两种策略。旧策略通过基准脚本显式恢复，不回滚生产源码。

| 指标 | 原串行、每侧四区域补检 | 并行、关闭补检 |
|---|---:|---:|
| 稳态吞吐（不含启动和界面绘制） | 3.99 FPS | 10.63 FPS |
| 手部管线耗时中位数 | 195.22 ms | 34.38 ms |
| 总耗时（含启动/收尾） | 47.75 s | 29.99 s |
| 输入帧数 | 120 | 120 |
| 回调错误 | 无 | 无 |

两组帧时间戳逐条完全一致；新版所有帧左右 `crop_attempts` 均为 0。稳态吞吐约提升 2.66 倍。证据：`results/performance/offline_pair_before_20261112` 和 `results/performance/offline_no_rescue_20261112`。

这段输入未检出手；因此该对照验证空场景性能和完整性，不证明有手场景的召回率。关闭补检后，原来只能靠裁剪发现的小手/边缘手可能漏检，这是用户指定的策略。以上为真实录制回放，不是新设备实拍；基准没有运行客户窗口深度计算和绘制，实际界面速度还受这些负载影响。

复现：

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_recorded_pipeline.py data/imu/session_20261111_105436_609132400 results/performance/new_before --frames 120 --legacy-policy
.\.venv\Scripts\python.exe scripts/benchmark_recorded_pipeline.py data/imu/session_20261111_105436_609132400 results/performance/new_after --frames 120
```

基准达到指定帧数后主动取消，会在回放摘要中写 `cancelled`；这属于有界测试，不应视作整段回放完成。原始录制只读，基准输出要求使用新目录。
